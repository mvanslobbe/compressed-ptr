Benchmarks

Measured on 12th Gen Intel Core i7-12700H, Linux, GCC 15.2, 2026-11-15. Release build (-O2), one pinned core (threads: eight cores). Reproduce with:

cmake -S . -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build
./build/bench_rss 2000000
./build/bench_runtime 4194304 10000 list     # or map, hash, arithmetic, ...

The plf::list results need a plf_list checkout (7.6.50 or later):

cmake -S . -B build -DCMAKE_BUILD_TYPE=Release \
  -DCOMPRESSED_PTR_PLF_LIST_DIR=/path/to/plf_list && cmake --build build
./build/bench_runtime 4194304 10000 plf
scripts/make_bench_page.py runtime.md rss.txt > docs/benchmarks.md

For a quick check on your own machine, run ./build/example_expect_gains: it prints memory per element and time per operation for each std container against its cptr counterpart.

Summary

  • Memory: the bundled containers use half the memory of the std ones.
  • Speed: against raw links in the same container, compressed links are mostly equal or faster once a structure outgrows the caches, because more nodes fit in each cache line and page. The exceptions: unordered_map find (about 15% slower here), pointer chases that fit in L1 or L2, and the slowest 1% of list shrinks. The tables below give every case.
  • Where it costs: a compressed pointer is decompressed with an add (and a conditional move or branch for null). On a pointer chase that fits in L1, that shows; nonnull_ptr removes most of it. Pointer arithmetic over arrays does not vectorise: convert to T* once for hot loops.

How the time is measured

bench_runtime uses nanobench. Each benchmark runs thousands of short epochs of a few hundred operations on a structure that stays large for the whole run, and reports the 50th, 90th, 95th, 99th and 99.5th percentile of the time per element. Each variant is compared with a reference at the same percentile: Δp99 = +10% means its p99 is 10% slower than the reference's p99. The reference is the same container with raw 8-byte links, or a raw T*. Variants run interleaved, in bursts of 8 epochs, so frequency changes and other drift affect all of them alike. Up to p99 two runs agree within a few percent; p99.5 is the 50th-slowest of 10,000 samples and moves more.

The compressed list grows faster than the raw one because it commits and touches half as much memory, and walks faster because twice as many nodes fit in a cache line. std::list pops faster: glibc's free is cheaper than the cage allocator's deallocate.

Each sort epoch first overwrites the list's values with fresh random ones, in list order, and the time includes that walk. plf::list sorts by copying node pointers into an array, sorting the array and relinking, so the link size matters less there than in a walk. With only about a hundred sort epochs, its p99 and p99.5 are a single slow epoch and move a lot between runs. The same goes for the slowest 0.5% of pops, which ranged from 50% faster to 48% slower over two runs; up to p95 they agree within a few percent. The memory table above has its bytes per element.

These keys are 0 to n − 1, inserted in random order. std::hash<uint32_t> is the identity, so std::unordered_map gives every such key a bucket of its own, which favours it at find. With keys spread over the 32-bit range (as in example_expect_gains), or with a mixing hash, cptr::unordered_map finds as fast or faster. std::unordered_map keeps its nodes on one list in allocation order, so it walks memory nearly in order; cptr::unordered_map walks bucket by bucket.

The raw loop is vectorised. A 32-bit offset that may wrap is not an induction variable the compiler can turn into a pointer, so the ptr loop stays scalar. In a hot loop over an array, convert to T* once with get().
